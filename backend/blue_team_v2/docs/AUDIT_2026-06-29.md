# TGIE Fraud Detection — Complete Logic Audit & Enhancement Plan
**Date:** 2026-06-29 · **Scope:** `backend/blue_team_v2/` (detection) **and** `backend/risk_engine/` (decision) · **Status:** audit only, no detection/decision code modified (Phase 1 directive)

Grounded in a line-by-line read of every module **and live execution** of both engines against the simulator, double-diamond variants, amount/timing sweeps, and legitimate-traffic scenarios. Every claim cites a `file:line` or a measured result.

---

## 0. Executive summary — the headline finding

**TGIE runs two independent fraud scorers, and the smart one does not make the decision.**

1. **Blue Team V2** (`blue_team_v2/`) — rich, evidence-based, per-node 18-factor, 11 detectors, classifications, narratives. Excellent recall.
2. **Risk Engine** (`risk_engine/engine.py`) — a separate, simpler cumulative 0–100 scorer.

In production (`api/routes.py:325-344`), Blue Team V2 runs first, then **`risk_engine.assess()` overwrites `risk_score` and `flagged`**, and **case creation is driven solely by `risk_engine`’s `should_create_case` (score ≥ 70)**. Blue Team V2’s verdict, evidence, mule-network/bridge/layering findings and classifications are computed and then **discarded for the decision** (they survive only as UI/`v2` payload).

The consequence, measured live:

| Input | Blue Team V2 verdict | **risk_engine (production decision)** |
|---|---|---|
| Double-diamond ₹9L/layer (w2) | FRAUD (0.91) | **score 53 · Suspicious · NO case** |
| Double-diamond ₹9L/layer (w4) | FRAUD (0.94) | **score 65 · NO case** |
| Layering chain (6-hop ₹800k) | FRAUD (0.90) | **score 49 · NO case** |
| Smurfing / fan-out / fan-in | FRAUD | **33 / 36 / 36 · NO case** |
| Mule network / cashout / bridge | FRAUD | **47 / 47 / 57 · NO case** |
| Circular / synthetic / hybrid / large-org | FRAUD | 71 / 74 / 87 / 86 · case ✅ |

**Production only auto-creates a case for 4 of 11 fraud archetypes, and misses the double diamond.** This is a **false-negative crisis in the decision layer**, masked by the fact that Blue Team V2 (which *does* catch them) isn’t wired to the decision.

The good news: the FPs that Blue Team V2 over-flags internally (payroll → FRAUD, marketplace → FRAUD) are **suppressed by risk_engine** (→ Monitor, no case), so they don’t reach production today. But the same disconnect that hides those FPs also hides the real detections.

**Single highest-impact change:** unify the two engines — let Blue Team V2’s evidence drive (or strongly inform) the `risk_engine` decision — then fix risk_engine’s recall (narrow-fan scoring + a reconvergence factor + calibration). Everything else is secondary.

## 1. Production decision path (traced)

`api/routes.py` ingest flow:
1. `route_all_components()` → Blue Team V2 adapter → `multi_verdicts` (V2 verdict + `v2` block). *(routes.py:31)*
2. For each component: `a = risk_assess(comp)` → **overwrite** `v["risk_score"]=a["score"]`, `v["risk_level"]`, `v["flagged"]=a["should_create_case"]`. *(routes.py:333-344)*
3. Case auto-created iff `assessments[gid]["should_create_case"]` i.e. `risk_engine score ≥ investigation_threshold (70)`. *(routes.py:354-362)*

So: **Blue Team V2 = evidence/explanation provider; risk_engine = the actual decision + case trigger.** They share no logic; risk_engine re-derives its own factors from the raw component and **never reads Blue Team’s evidence/patterns** (it only reads `node.detected_patterns`, which the live graph rarely populates).

## 3. Phase 5 — Why the Double Diamond is not classified as fraud (root cause, proven)

**It is the production decision layer, not the detector.** `risk_engine.assess()` scores a material double diamond **53–65, below the case threshold of 70**, so no case is created and the live graph shows “Suspicious” at most. Decomposition of the w2 ₹9L score (≈53):

| risk_engine factor | value | points (intensity×weight) |
|---|---|---|
| layering depth | longest path = 5 → intensity 1.0 | 22 |
| amount | ₹4.5L → band 0.60 | 15 |
| fan_out | max_out = **2** → (2−1)/9 = 0.11 | ~2 of 20 |
| fan_in | max_in = **2** → 0.11 | ~2 of 20 |
| velocity / complexity | small | ~5 + ~6 |
| circular | none | **0 of 25** |

Why it falls short of 70:
1. **Narrow fans score almost nothing.** `fan_out/fan_in` intensity = `(max−1)/9` (`engine.py:119-120`), so a 2-way diamond split earns ~2/20. Diamonds *are* narrow by definition.
2. **No reconvergence factor.** The diamond’s defining structure — split then re-merge on a shared node — contributes **zero**; risk_engine has no concept of it.
3. **The 25-pt `circular` factor is the biggest single lever**, and a diamond is acyclic → 0.
4. **Blue Team V2’s evidence is ignored.** In V2 the same graph trips `mule_accounts + bridge_accounts + layering + cashout + hybrid_network` → FRAUD 0.91. None of that reaches the decision.
5. **Threshold/recall mismatch:** even a textbook 6-hop layering chain scores 49 < 70.

Secondary cause (affects Blue Team V2’s own evidence, relevant once wired): **amount-gating cliff** — every V2 detector has a hard ₹ floor (layering ₹25k/hop, fan ₹150k vol, mule ₹50k, bridge/cashout ₹100k). A double diamond at ≤₹48k/layer trips **zero** V2 patterns (verified), so even the evidence layer goes quiet on small-value structuring.

**Fix:** (a) feed V2 evidence into the decision; (b) add a reconvergence factor to risk_engine; (c) make narrow-but-deep split/merge score materially; (d) convert V2 detector gates from binary to graded.

## 5. Logical weaknesses (consolidated)
1. **Two disconnected scorers; the weaker one decides.** (architecture) — *the* defect.
2. **Decision-layer false negatives**: 7/11 archetypes + double-diamond below the 70 case threshold.
3. **No reconvergence/split-merge model** in either engine (diamond signature invisible).
4. **Amount-gating cliff** in V2 detectors (sub-gate structuring evades evidence).
5. **No legitimacy model in V2** (payroll/marketplace/vendor → FRAUD internally).
6. **smurfing/cashout/fan over/under-trigger** as above.
7. **hybrid_network over-labels** simple fraud as organised crime.
8. **Dead/duplicate factors**: `bridge_importance == betweenness`; `closeness`/`degree`/`rails` computed, never used; “18-factor” is really 16.
9. **Stateless per component**: no repeated-beneficiary/originator across cases, no historical baseline, no entity resolution.
10. **Magic numbers** scattered across V2 detectors (risk_engine already externalises its config — good; V2 should too).

## 7. Improved architecture (specific)

### 7.1 Unify the decision (CRITICAL)
In `risk_engine.assess`, accept the Blue Team V2 result and add factors: `bt_max_evidence_severity`, `bt_distinct_families`, `bt_top_pattern` (reconvergence/mule/circular/cashout weighted high). Keep risk_engine as the *governor* (suppressor, threshold, config) but let V2’s evidence raise the score so a double-diamond/layering/mule case clears 70. Alternative: drive the decision from V2’s `cluster_risk` and keep risk_engine’s suppressor as a veto. Either way, **one decision informed by all detectors.**

### 7.2 Reconvergence detector (new, both layers)
For node `M` with ≥2 predecessors sharing a common ancestor `S` within k hops (split→merge), emit graded `reconvergence` evidence scaled by parallel-path count, re-converged/originated value (conservation), and tightness. Chain detections → graded `double_diamond` multiplier — never a hardcoded shape.

### 7.3 Legitimacy model (new) — fixes V2 FP
Per-component `legitimacy_score` from account_type (merchant/employer/govt), payee-set stability, periodicity, **amount diversity** (legit businesses pay varied amounts; structuring is uniform — invert today’s logic), and “hub pays many terminals that don’t forward” (payroll has no onward chain). Subtract in V2 scorer and feed risk_engine’s suppressor.

### 7.4 Fix detectors
- **smurfing**: threshold-proximity + forwarding + no-legitimacy (drop bare identical-amount).
- **cashout**: require cash/ATM/exchange type OR implicated upstream (not a plain merchant collector).
- **fan thresholds / gates**: graded evidence below ₹ floors instead of zero.

### 7.5 Cross-component entity layer (new)
Persistent store keyed by account: lifetime counterparties, prior verdicts, first/last seen → repeated-beneficiary/originator, dormancy-vs-baseline, relative velocity.

## 8. Explainability & code quality
- **Explainability** is already strong in V2 (contributors, narrative, classifications) and risk_engine (`explanation`, `top_indicators`, `suppression_reason`). Add: “benign hypotheses considered & rejected”, surface `legitimacy_score`, and **show both engines’ views** in the case so the disconnect is visible to investigators. Today an investigator sees risk_engine’s score but not that V2 flagged a mule network.
- **Code quality**: remove dead `score_to_action` (`types.py:60`), duplicate `bridge_importance`, unused `closeness`/`degree`/`rails`; correct the “18-factor” doc; centralise V2 magic numbers into a config like risk_engine already has; add `diamond`/`double_diamond`/`payroll`/`marketplace`/`vendor`/`structuring_true` simulator archetypes so the benchmark measures **precision and recall on hard cases**, not just easy ones (today it flatters both engines).
